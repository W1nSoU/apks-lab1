## 1. Огляд та проблеми, які вирішує агент

Розробка сучасного кросплатформного програмного забезпечення вимагає значних витрат часу на рутинні операції:
- Створення стандартної файлової структури проєкту.
- Налаштування дескриптора складання (`pom.xml`) з правильними версіями плагінів та залежностей.
- Створення юніт-тестів для перевірки базової бізнес-логіки.
- Написання окремих скриптів автоматизації для різних сімейств ОС (POSIX shell для Linux/macOS та Batch для Windows).
- Складання коректного YAML-маніфесту для CI/CD сервісів (GitHub Actions) з урахуванням специфіки кожної ОС у матриці.

**AI-агент `build-engineer`** вирішує ці проблеми шляхом повної автоматизації життєвого циклу ініціалізації та конфігурації проєкту, забезпечуючи стандартизацію, повторюваність, безпеку та надійну верифікацію.

## 2. Компоненти системи

### 2.1. Agent Manifest (`.github/agents/build-engineer.agent.md`)
Центральний опис агента, що визначає:
- **Роль:** Build & CI/CD Automation Engineer.
- **Область відповідальності:** генерація коду, тестів, конфігурацій та скриптів.
- **Правила безпеки:** сувора заборона руйнівних дій (перезапис історії Git, витік секретів, видалення файлів поза межами проєкту).
- **Критерії завершення (DoD):** наявність усіх артефактів, успішне проходження локальних тестів, успішний білд `target/hello.jar`.

### 2.2. Навички (Skills)
Модульні багаторазові інструкції для спеціалізованих задач:
1. `project-scaffold`: створює скелет проєкту, дерево пакетів Java та `.gitignore`.
2. `build-and-test`: створює конфігурацію Maven (`pom.xml`), вихідний код `App.java`, юніт-тести `BasicAdditionTest.java` та скрипти `ci.sh`, `ci.bat`.
3. `github-actions`: формує матричний робочий процес `.github/workflows/ci.yml`.

### 2.3. Команди (Commands)
Користувацькі іменовані команди:
- `git-init` — ініціалізація Git та налаштування `.gitignore`.
- `create-project` — виклик скіла `project-scaffold`.
- `create-build` — виклик скіла `build-and-test`.
- `create-actions` — виклик скіла `github-actions`.
- `check` — перевірка структури, запуск компіляції та тестів (read-only перевірка).
- `init` — оркестратор повного циклу.

## 4. Передача даних між етапами

Кожен крок передає наступному гарантовано валідний стан файлової системи:
1. `git-init` гарантує наявність репозиторію та правил ігнорування `target/`.
2. `create-project` створює файлову структуру, на яку покладається `create-build`.
3. `create-build` створює виконувані скрипти `ci.sh` та `ci.bat`, на які посилається `create-actions`.
4. `create-actions` створює `ci.yml`, перевірку якого здійснює `check`.
5. `check` читає всі створені артефакти, запускає компіляцію та формує фінальний звіт.

## 5. Обробка помилок оркестратором

Оркестратор `init` реалізує стратегію **Fail-Fast**:
- Після виконання кожної окремої команди аналізується код виходу (`exit code`).
- Якщо код виходу `!= 0`, процес негайно призупиняється.
- Формується діагностичне повідомлення із зазначенням конкретного кроку, файлу та причини падіння.
- Навмисне пошкодження перевірки (наприклад, зламаний юніт-тест або відсутність `ci.sh`) блокує успішне завершення оркестрації та виводить чітке попередження про помилку.
- Повторний запуск є ідемпотентним і не призводить до втрати вже валідного коду.
